# Дизайн веб-интерфейса

Этот раздел фиксирует не гейм-дизайн и не архитектуру приложения, а правила
проектирования веб-интерфейса: как экран игры должен жить на телефонах,
планшетах и больших мониторах.

Архитектурные документы в `docs/architecture/` не меняются этим слоем. Здесь
описываются только интерфейсные решения: размеры, плотность, адаптивность,
поведение панелей и ограничения ширины.

## Цель

Первый целевой результат: игра должна хорошо выглядеть и быть удобной на
телефоне около `380x830`.

После этого тот же интерфейс должен:

- на чуть больших телефонах получать больше воздуха, а не другую структуру;
- на `1024x768` переходить в базовую планшетную/малую desktop-композицию;
- на больших экранах масштабироваться через свободное пространство и
  ограничение максимальной ширины, а не через бесконечное растягивание блоков;
- на `2560x1440` выглядеть как аккуратно ограниченный интерфейс, а не как
  растянутая мобильная верстка.

## Актуальные контрольные размеры

Проверочные viewport'ы для интерфейсных решений:

| Размер | Назначение |
| --- | --- |
| `384x832` | минимальный близкий к реальным телефонам baseline |
| `390x844` | основной iPhone-подобный телефон |
| `393x852` | основной Android/iPhone-подобный телефон |
| `402x874` | телефон с небольшим запасом высоты |
| `428x926` | крупный телефон |
| `440x956` | крупный телефон с большим запасом воздуха |
| `1024x768` | базовая планшетная/малая desktop-композиция |
| `2560x1440` | широкий desktop с ограничением контента по ширине |

## Стратегия адаптивности

Интерфейс проектируется mobile-first.

Базовая сборка делается под узкий телефон: ширина `380-390`, высота около
`830-850`. На этом размере должны быть видны основные игровые действия,
текущий контекст и понятный способ добраться до вторичных панелей.

На телефонах `402-440` структура не перестраивается. Добавляется воздух:
чуть больше вертикальных отступов, комфортнее списки, меньше ощущения сжатости.
Новые обязательные зоны интерфейса на этих размерах не появляются.

На `1024x768` интерфейс получает первую полноценную перестройку: панели могут
становиться видимыми рядом с основным контентом, но центральная игровая область
остается главным объектом. Этот размер считается базой для desktop-модели.

На больших desktop-экранах интерфейс не растягивается до краев. Работают:

- `max-width` для основного контента;
- центрирование рабочей области;
- дополнительные внешние поля;
- более свободные, но не гигантские расстояния между зонами;
- ограниченная ширина текстовых блоков и логов.

## Практические правила

- Начинать проверку с `384x832` или `390x844`, а не с desktop.
- Не прятать критические действия ниже первого экрана без явного sticky/drawer
  механизма.
- Не делать отдельный дизайн для каждого телефона из списка. Список нужен как
  набор контрольных точек, а не как семь разных макетов.
- Использовать drawer/overlay для вторичных панелей на телефонах.
- Не растягивать строки текста, боевые логи и карточки на всю ширину 2K-экрана.
- На desktop добавлять воздух и ограничивать ширину, а не увеличивать все
  шрифты и карточки пропорционально экрану.
- Для игровых экранов сначала защищать центральную область, потом размещать
  вторичные панели.

## Definition of Done для экрана

Экран считается готовым по responsive-дизайну, когда он проверен минимум на:

- `384x832`;
- `390x844`;
- `428x926`;
- `1024x768`;
- `2560x1440`.

На каждом размере должны быть выполнены условия:

- нет горизонтального скролла страницы;
- важные действия доступны без угадывания;
- текст не налезает на соседние элементы;
- центральная игровая область не теряется среди панелей;
- desktop-версия ограничена по ширине и не выглядит растянутой.
